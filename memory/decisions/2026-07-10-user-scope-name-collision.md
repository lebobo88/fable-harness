# Decision: known limitation — FABLE-HARNESS agent names collide with pair-programmer's at user scope

**Context**: While smoke-testing the `install-user-scope` skill's dry-run mode (Phase 6), the installer correctly detected that `~/.claude/agents` and `~/.claude/skills` are whole-directory symlinks into `H:\pair-programmer\.claude\...`, which already contains agents with the *same names* as 30 of FABLE-HARNESS's 32 agents (only `meta-agent` and `verifier` are new names). This is a direct consequence of an earlier design decision: FABLE-HARNESS's agent roster was deliberately modeled on pair-programmer's own real, proven agent registry (per `plan.md`'s "Agent roster" section), reusing the same names for the same conceptual roles.

**Effect**: The merge-safe installer (CONSTITUTION N11) correctly `SKIP`s every name collision rather than overwriting — this is the safe, intended behavior, not a bug. But the practical consequence is that running `/install-user-scope` today only adds `meta-agent.md` and `verifier.md` to user scope for use in *other* projects; the other 30 domain/orchestration agents remain shadowed by pair-programmer's same-named versions when working outside H:\FABLE-HARNESS.

**Does this affect FABLE-HARNESS itself?** No. Claude Code's own resolution priority for subagents is `managed > CLI flag > project > user > plugin` — project scope always wins over user scope. Inside H:\FABLE-HARNESS, its own `.claude/agents/*.md` files are used regardless of what's symlinked at user scope. This limitation only affects reusing FABLE-HARNESS's specific agent *implementations* (their exact CONSTITUTION-citing bodies, I/O contracts to `.fable/<run_id>/...`, etc.) from a different project.

**Alternatives considered**: (a) accept as a known, documented limitation (chosen); (b) rename all 32 FABLE-HARNESS agents with an `fable-` prefix to avoid any collision — rejected for now as an invasive rename touching every already-built agent, skill, and workflow cross-reference, for a benefit (cross-project reuse of the exact same-named role) that's speculative until an actual cross-project reuse need arises; (c) let the user choose per-agent at install time which implementation wins — deferred as unnecessary complexity for a v1.

**Chosen**: (a). Document the limitation plainly (this file, and a note added to the `install-user-scope` skill's dry-run output already surfaces it live to the operator every time the skill runs, since the dry-run lists every SKIP explicitly).

**Owner**: harness maintainer. **Review date**: revisit if/when there's an actual need to use FABLE-HARNESS's specific agent bodies (not just pair-programmer's same-named ones) from a different project — at that point, a `fable-` prefix rename (or a smarter per-agent override mechanism) is the concrete next step.
