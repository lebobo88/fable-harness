- **mythic-proportion Phase 6 local privacy layer — security invariants**: (1) **No raw PII ever crosses the machine↔cloud boundary.** When redaction is enabled, the redact→LLM→rehydrate wrapper masks PII locally BEFORE the outbound cloud request is built; there is no code path where un-redacted note content (Confidential/Restricted) reaches `httpx.post`. (2) **Redaction is FAIL-CLOSED**: any error from Presidio/torch/the recognizer aborts the cloud call and raises — it never degrades open to sending raw content. (3) **The rehydrate map (masked-token→original-PII) is per-request, in-memory only** — never logged, cached (not in `LlmCache`), persisted to `.mythic.toml`, sent upstream, or placed in any response field. (4) **`local: true` makes ZERO non-localhost network calls** for compile/query/extraction — it routes entirely through the Ollama loopback provider (`localhost:11434`) and has NO fallback-to-cloud on Ollama error. (5) **Embedding inference is on-device**: chunks never leave the machine; only a one-time model-weights download (carrying no user content) is permitted; HashEmbedder remains the zero-dependency fallback. (6) **The base install (no `[privacy]`/`[embeddings]`/`[local]` extras) still imports and runs BM25-only** — presidio/torch/fastembed/httpx are lazily imported, with no import-time network activity and no hard dependency. (7) **Credentials remain env-only** (`AUTHHUB_API_KEY`/`ANTHROPIC_API_KEY`) — never in `.mythic.toml`, logs, errors surfaced to the SPA, or test captures. (8) **No log/telemetry line carries Confidential (note text/chunks) or Restricted (PII/rehydrate map/credentials) data** — counts, masked tokens, and timings only. (9) **The `/api/query` omitted-`mode` legacy response shape is preserved byte-for-byte** by inserting redaction (redaction is transparent to the response contract; the preceding mode-contract invariant is preserved, not weakened). A later revision must not weaken any of these without a fresh `security-reviewer` review. NOTE: these are recorded as binding requirements at security-design time; the Phase 6 implementation (`privacy/redact.py`, `llm/ollama.py`, embedder default flip, provider selector, Settings view) did not yet exist at recording, so the security-reviewer verdict for this stage is `reject` (N4 fail-closed) until the code exists and proves these via the specified tests. (recorded 2026-07-11, by security-reviewer, run 20260711-202730-p6-privacy-layer)
- **run.js section scheduling**: sections are dispatched in **two dependency waves**, never one flat concurrent `pipeline()`. Wave 1 is every *producing* section; wave 2 is every section in `DESCRIBES_OTHER_SECTIONS` (currently `4.13` — docs/changelog/release notes), which documents what the other sections built. The barrier between waves is deliberate and required: wave 2 cannot describe wave 1's output truthfully until that output is actually on disk. Running them concurrently made `4.13-docs-author` write a changelog for code `4.8-engineer` had not written yet, which its judge then correctly rejected for describing unearned work — a **scheduling defect misreported as a judging defect**, leaving the whole run falsely `surfaced` rather than `finalized`. Reproduced twice consecutively (runs `20260726-213456-p1-render-foundation` and `20260726-221514-p1-black-frame-fix`, SOLAR FRONTIER Phase 1); same failure class as the earlier `20260711-141439-p1-design-system` false-negative already recorded above. Exception preserved: when `4.13` is the ONLY mapped section (the trivial-scope taxonomy floor) it has nothing to wait for and must run in wave 1, or the run produces no stages at all. A later revision must not collapse the waves back into a single `pipeline()` call, and must add any new section whose artifact describes another section's output to `DESCRIBES_OTHER_SECTIONS` rather than relying on luck in scheduling order. (recorded 2026-07-26, by main-loop, runs 20260726-213456 / 20260726-221514)

- **Artifact-authoring agents must re-read every cited value from disk at write time**: docs/changelog stages have been rejected for the SAME defect three times — runs `20260726-213456-p1-render-foundation`, `20260727-081003-p1-far-layer-queue` and `20260727-090143-p1-lighting-close-out` — each time because specific values in the artifact did not match the shipped code. Run `20260727-090143` is the clearest case: the run's CODE was good (all three defects genuinely fixed, operator-confirmed in a real browser) while its changelog cited fill-light values and linear-RGB arithmetic that did not match `Scene.tsx`, described a change that never landed, and reported 45/45 tests when the suite was 47/47 — the stale count having been copied from the request prompt, which was accurate when written and false by the time the artifact was authored. Judges must treat a cited-value/shipped-code mismatch as an N4 false-verification claim and reject. A later revision must not relax this into "describe the intended change" — the artifact documents what shipped, not what was planned. (recorded 2026-07-27, by main-loop)
